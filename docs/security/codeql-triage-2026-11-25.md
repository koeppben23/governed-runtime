## Isolation evidence for #87, #92, #93 and #94

Both operator harnesses require an explicit fresh `--root`; config, evidence and workspaces are placed below it. The risk-trigger harness creates evidence with mode `0700`, and the reviewer harness writes only installed fixture files below the workspace it was given. Neither harness starts a second concurrent host against the same root.

Remaining assumptions for owner approval: the operator owns the root exclusively, the root is fresh, and no concurrent local writer modifies it during the run. These are operator-contract assumptions, not properties enforced by the filesystem. Approval must confirm them per alert.

## Residual production risk — #103

Alert #103 is not claimed as fully eliminated. The implementation pins the inspected inode and rejects a changed identity immediately before `unlink`, but Node provides no portable unlink-by-fd operation. The trust boundary is the local operating-system user's plugin root; an attacker must already have concurrent write access there. The residual impact is a path swap between revalidation and unlink deleting a different regular file inside that root. This requires an explicit individual owner approval like any other accepted risk; it is not treated less strictly because it is production code.

## Accepted risks — owner decision required

The five accepted-risk findings require individual owner decisions: four operator-run harnesses under the isolation assumptions above, and the production uninstall residual described in the previous section. They are not classified as harmless merely because they are not shipped. Until all five approvals are recorded here and in the PR review, the release remains blocked.
